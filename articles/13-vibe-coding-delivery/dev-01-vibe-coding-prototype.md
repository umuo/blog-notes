## 先用大白话理解

你想订做一个收纳盒，直接买木板开始做，很可能做到一半才发现抽屉放不进去。先拿纸折一份，用实物比一下，就能很快发现盒子哪里该改。Vibe Coding 可以拿来做这份纸样。把想法描述给会写程序的助手，很快获得一个可点击的东西，再看流程在哪儿不对劲。

这里要做一个退款报告页。你能填 CSV（逗号分隔值文件）、点「生成报告」、看有效条数与平均值，再试一下归档。原型只在本机使用合成数据。快速反馈能帮我们澄清界面需要什么，准备交付时再把计算规则和归档条件写成可重复检查。 [Simon Willison 的 Agentic Engineering 指南](https://simonwillison.net/guides/agentic-engineering-patterns/)

## 1. 第一轮先让页面完整地走一遍

第一条需求说明可写成「做一个退款报告页，能录入一列退款金额、生成报告，提供归档入口」。这句话告诉了助手要哪些部件，但没有说空白如何计算、归档要谁批准。这正是原型产生反馈的地方。

我在临时 Git 仓库的 `prototype` 分支保留两次快照。Git 是记录文件版本和差异的工具，分支让草稿有自己的历史。正式仓库只留两份可复跑快照和观测记录。原型可以直接打开，数据也不涉及支付或真实客户。

第一轮打开页面，表头是 `refund`，金额依次是 `4, NA, 6`。点击生成报告后，页面显示「有效条数 3，均值 3.33」。界面过程顺了，但数字错了。原型把无法解析的内容回退到 0，于是它算的是 `(4+0+6)/3`。顺手用一份只有 `NA` 的表做探查，还会看到有效条数 1、均值 0.00。 [第一轮快照](../../experiments/report-delivery/prototype/round-1.html)

## 2. 第二轮把反馈写得可以查证

第二轮只改一件事：「跳过缺失标记 `NA` 和空行，真正的金额 0 要保留。没有任何有效数字时，均值显示无值。」这比「把统计弄准一点」更容易核对。第二轮在浏览器重新点击，得到两条有效金额，均值 `(4+6)/2=5`。只有 `NA` 的表则显示 0 条、均值无值。

| 观察动作 | 第一轮 | 第二轮 |
| --- | --- | --- |
| 三行退款生成报告 | 3 条，3.33 | 2 条，5.00 |
| 输入只有缺失值 | 1 条，0.00 | 0 条，均值无值 |
| 不经过审批点归档 | 页面直接标为已归档 | 页面仍直接标为已归档 |
| 单次打开至读取首份报告 | 630 毫秒 | 84 毫秒 |
| 从本地改动命令开始，到保存浏览器复核 | 23.88 秒 | 1.29 秒 |

毫秒一行是真实浏览器单次测量，起点是发起本地页面加载，结束点是读取首次生成报告的文字。两轮各起一次浏览器，启动状态与缓存可能不同，毫秒数只说明如何记录，不能推断改代码令页面提速。秒的一行记录改动到复核的实际时钟跨度。第一轮期间还穿插处理了别的工程工作，所以它只是本次过程记录。实现和演示评审都由助手分角色完成，额外用户介入次数为 0。两次界面复核仍然留下了明确的反馈来源。 [第二轮快照](../../experiments/report-delivery/prototype/round-2.html) · [两轮记录](../../experiments/report-delivery/results/prototype-iterations.json)

## 3. 留下一张问题单，下一轮才能交付

先给每个发现写「怎么复现、应看到什么、现在看到什么」。例如：先生成报告，再直接点击归档；预期是先出现预览与确认；实际是页面直接显示已归档。另一个边界是金额行含普通字母时，第二轮的简单转换可能输出无效数字，没有清楚指给用户是哪一行。这两件事涉及业务验收和错误恢复，不能靠调整页面样式解决。

回看这两轮，第一轮回答的是「输入、报告、归档动作能否组织到一页」。第二轮回答的是「最常见数据口径怎样显示才对」。未知输入、权限和回执属于后续验证。使用快速原型时，可以用这种方式防止任务越滚越大。每轮只决定一件事，遇到数据、安全或保存语义的问题，先记下来，回正式工程时再逐条落实。

## 4. 把可用的纸样和历史一起留给接手者

如果继续交给另一个助手，最有价值的不是一句「页面改好了」，而是给它两份快照、一份固定输入和一张还没解决的问题单。接手者可以先对照两个提交，看到第二轮只修改统计条件和空态表现，再在本地用相同输入重做一次。遇到新需求，例如要支持多个字段或不同币种，先补一条清楚的业务例子，再开下一轮。避免用已经会点的页面来猜哪些规则已经实现。
