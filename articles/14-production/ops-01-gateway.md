## 先用大白话理解

退款报告页算出了平均退款 5.00 元。下一步请大语言模型（Large Language Model，简称 LLM）写一段说明。想象两个模型供应商各有一个柜台，报告应用统一到接待处取号。接待处会检查还能收几个请求、该送到哪个柜台、有没有一份可直接复用的答案。这个接待处就是模型网关（LLM Gateway）。

全文使用同一个输入。逗号分隔值文件（CSV）里有 `8.00`、`2.00`、`NA`，其中 `NA` 表示缺失。统计工具算出 2 条有效记录、均值 5.00 元。模型只收到这份汇总和报告写作要求。业务应用随后负责是否归档。

## 四道限额分别限制什么

一次请求要预估输入和最多输出的 Token，也就是模型用来处理文本的片段。例子预留输入 900、输出 200，共 1,100 Token。“最多用多少”和“最后实际用了多少”分别用于入场和对账。同一个分钟窗口中，演练配置如下。

| 名称 | 保护什么 | 例子 |
| --- | --- | --- |
| RPM（Requests Per Minute） | 每分钟请求数 | 2 个外部请求，第三个收到 `429` |
| TPM（Tokens Per Minute） | 每分钟可用的 Token 数 | 2,200 Token，预留 1,100 后还剩 1,100 |
| 并发上限 | 同时进行中的工作数 | 占用唯一执行槽时，下一条回并发限额 |
| 费用预算 | 累积费用 | 余额 9 个模拟计费单位，每次尝试先预留 3 |

RPM 针对应用接入，TPM 和费用在此例针对供应商尝试。A 失败后 B 也要预留 1,100 和 3，外部请求仍只算 1 个。断流时在 `finally` 释放执行槽。固定窗口在边界允许突发，两个网关副本还需要共享原子计数器来守住总额度。真实账本要用供应商返回的用量结算，超时则保留待对账项。预算不足时应在调用前明确返回拒绝原因。供应商自己的计数和限额需依据接口文档处理。 [OpenAI 限额指南](https://developers.openai.com/api/docs/guides/rate-limits)

## 请求怎样挑供应商

网关可以把 `refund-summary` 当作应用使用的逻辑模型名，先按数据地域、输出格式和工具支持筛出可用部署，再按期限、健康状况和成本排序。若这次要求固定字段 `rows` 和 `mean_cents`，备用部署也得通过同样的结构验证。网关的路由版本要随请求记录，回查时才知道当时有哪些候选。LiteLLM 的 Router 文档提供跨部署路由、重试、冷却和超时设置，业务仍要给出可替换的语义条件。 [LiteLLM Router](https://docs.litellm.ai/docs/routing)

应用给整个调用 2 秒时，可以给 A 预留 800 毫秒，再根据剩余时间决定是否试 B。连接刚建立时返回的 `429` 表示供应商在当前条件下请求过多。优先读取供应商提供的等待指示，配合退避和随机抖动，避开所有请求同时重试。演练中选择立即试已预授权的 B。验证、权限等确定性拒绝交给调用端处理。超过整条请求的期限就结束，避免每层各自重试三次，把一个调用放大成九次。

## 发出第一个片段后，降级边界变了

流式返回常走 SSE（Server-Sent Events，服务器发送事件），客户端可以边收边显示。A 尚无应用事件送出时，可以换 B，再由 B 生成完整结果。若 A 已经发出“这次退款共”，客户端随后接上 B 的“有效记录有两条”，用户看到的是两次生成拼成的一句话。切换前要知道哪些数据已可见，包含生成文本、工具调用片段和业务事件。此例拒绝续拼，标记 `stream_error:incomplete`，界面保留未完成标记。支持重开时给新的尝试号并明确重置。写入动作必须在服务端校验已完成、结构合法且取得授权后才执行。

## 命中缓存拿回什么

提示词缓存保存匹配前缀的计算状态，像每次填报告前先备好相同的表头，模型仍生成这一单的答案。完整响应缓存直接返回以前的答案，像拿出同一版已经写好的报告。演练采用后者，缓存键包括租户、输入摘要、报告版本与路由版本。应用先做身份和访问检查，再查缓存。生产还需让相关权限范围、输出配置、输入及数据版本参与键或失效条件，并控制存活时间。会变化的数据、带副作用的工具步骤和断流结果不入缓存。提示词缓存的实际计费和限额依供应商而定。 [OpenAI 提示词缓存机制](https://developers.openai.com/api/docs/guides/prompt-caching)

## 跟一遍故障回放

从[生产化演练](../../experiments/production-refund/README.md)运行脚本，看输出中的 `OPS-01`。供应商以固定事件替代，所有分支都在虚拟窗口内执行。

| 输入 | 观察到的事件 |
| --- | --- |
| A 在首个事件前返回 429 | `A:429 → B:ok → done` |
| A 在首个事件前超时 | `A:timeout → B:ok → done` |
| A 发出部分内容后断开 | `A:partial → stream_error:incomplete` |
| alpha 连续请求两次，第三次仍在同一分钟 | 第一次访问 A，第二次命中响应缓存，第三次 `429:rpm` |
| beta 请求同一摘要 | 重新访问 A |
| 预留 2,201 Token、占满执行槽或费用余额低于 3 | 分别命中 TPM、并发、预算拒绝 |
| 费用余额 5，A 返回 429 | A 预留 3，剩余 2，拒绝调用 B |

生产上可给网关记录 `attempt_id`、供应商、耗时、路由版本、缓存命中、实际用量和终态。遇到“模型成功但用户看到了半截”时，从客户可见终态反查。网关只决定模型请求怎么走，归档决策由下一篇的工具权限处理。 [生产化专题目录](../../llm-agent-learning-roadmap.md)
