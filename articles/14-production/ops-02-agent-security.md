## 先用大白话理解

前台帮你打印报告，保管员才有库房钥匙。保管员还得核对签字里的报告编号、目的地和有效期。生产里的 Agent 也一样，应用先给它算账用的钥匙。需要归档时，再由拥有归档权限的服务拿着明确的批准执行。

本例上传 CSV（Comma-Separated Values，逗号分隔值文件），计算退款金额 8.00 元、2.00 元和一个缺失值 `NA`。结果有 2 条有效记录，均值 5.00 元。用户在预览看到的报表就是要批准的文档。环境、租户、任务、文件和动作范围都需要由服务端以可信数据确定。

## 把四道边界落到四个执行点

| 要解决的事 | 服务在哪里把关 | 例子 |
| --- | --- | --- |
| 谁来请求 | 登录服务给用户身份，运行时用独立工作负载身份 | 统计进程可以读本任务，归档进程只能消费明确授予的操作 |
| 能读写什么 | 工具后端核对租户与任务，沙箱只挂当前工作目录 | 任务 `r-17` 的临时输入和报告草稿 |
| 能往哪里发 | 网络出口限制连接，应用归档服务限制目标和对象路径 | 租户 alpha 仅能归档到 `archive-a` |
| 何时允许归档 | 归档后端对照批准记录和当前策略 | 当前报告摘要匹配、审批人有效且在有效期内 |

访问令牌交给归档服务自己使用，权限限制到具体租户和目标。模型只能提交结构化动作请求。即使模型说“已经获得批准”，归档服务仍自己查询审批，再从可信任务存储读取实际产物并计算摘要。可将归档分成两阶段，准备阶段返回只读预览和候选目标，确认阶段才提交。用 [DEV-03 的浏览器接管演示](../13-vibe-coding-delivery/dev-03-computer-use.md) 可以看到两次动作的界面差异。

## 一份批准到底绑定了什么

一份批准记录至少绑定 `actor`（授权人）、`tenant`（租户）、`run`（任务）、动作类型、`digest`（报告字节摘要）、`target`（目标库）、`policy`（经批准时的策略版本）与 `expires_at`（失效时刻）。样例动作类型固定为归档，教具将这些字段封装在 `ArchiveRequest` 中。报告只要变一个字也要重新验摘要。即使新报告的均值仍是 5.00 元，它也需要对应新的批准。如果授权人已被撤权，归档后端在提交时重新按当前身份和策略裁决。

实际写入时，把审批消费与操作唯一键写入同一持久化事务，或使用目标端支持的幂等标识，同一个操作重复提交时返回已有收据。要确认有效期和授权状态至少经历最后一次提交检查。对象写入与数据库是两个系统时，还需要核对写入结果并处理未知终态，详见后面的服务迁移一篇。 [审批设计与归档](../09-security-guardrails/sec-05-tool-approval.md)

## 网络规则与工具规则一起生效

在 Kubernetes 中可以给执行沙箱设置默认拒绝出口，再只允许访问报告所需的内部代理。NetworkPolicy 依赖集群网络插件的执行支持。策略以允许项叠加，检查时要查看同时选中该工作负载的其他策略。它解决到哪些端点建立连接的问题，对“调用归档接口时这份报告属于谁”的判定还要归档服务自己做。域名和应用层目的地限制交给受管出口组件。管理员在测试命名空间分别运行一条允许连接和一条预期被拒连接，把网络结果与归档服务的决策记录分开看。 [Kubernetes NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/)

策略变更时，开发环境先跑规则级矩阵，预发布环境用与生产等价的限制验证真实执行点和运行身份，生产用隔离测试租户验证关键接入。不同环境分别签发身份，测试身份只允许对模拟目标执行。新旧策略差异应附部署环境、所影响的动作、回滚版本与负责人。收集决策原因时，避免把完整 CSV、令牌和报告全文写进审计。

## 六条输入回放给了什么结果

[演练脚本](../../experiments/production-refund/README.md)用固定身份和批准模拟决策点。批准人 `approver-a` 在预发布同意了租户 alpha 的报告，批准到虚拟时刻 50 失效，策略版本 `p-7`。

| 操作 | 结果 |
| --- | --- |
| 预发布、同一报告、同一目标、时刻 40 | `allow` |
| 把同一请求送到生产 | `identity_denied` |
| 把目标改到范围之外 | `target_denied` |
| 把报告换成另一份 | `approval_invalid` |
| 恰好在时刻 50 请求 | `approval_invalid` |
| 策略服务不可用 | `policy_unavailable` |

脚本检查六个策略判定，归档写入、真实网络阻断和租约身份采用集成测试验证。出现异常时，先定位决策日志里的任务号、动作和策略版本。若疑似授权错误，可先冻结归档动作、吊销相关身份、保留收据和出口审计，接着按同一任务号核对目标侧是否已写入，再恢复必要的只读任务。预案要写清谁可以停止归档、谁可以确认恢复，以及怎样核对历史收据。 [生产化专题目录](../../llm-agent-learning-roadmap.md)
