## 先用大白话理解

快递站有两个人。一个负责发件，另一个负责看哪些包裹总被退回来。第二个人可以提出「地址这一栏经常漏填，应该加检查」，再找人验证和批准。他不用自己发件，也不用动顾客的地址。这就是把正常业务和改进工作拆开。

同理，退款报表程序照常跑，一个独立观察 Agent 只读脱敏日志与指标。它能提交候选流程或测试建议，发版权限留给审阅流程。确定性实验用两个固定角色模拟这条链，可以先把合同和预期状态弄清，之后再接真实观测系统。

## 1. 先找到可复现的失败

Trace（追踪）把一次请求经过的处理阶段串起来。Trace ID 是这条链的标识。本例事件保留追踪标识、应用版本与错误分类。观察角色按 Trace ID 去重，再按旧版与错误类型聚合。三条缺失规则错误事件里，有两条来自同一次请求，所以只计两次独立失败。另一条格式错误归为单独一组。生产采集还可以保留命令耗时、Token（文本计量单位）和单位成本。应按数据处理政策决定采集范围。 [OpenTelemetry 的 GenAI 观测示例](https://opentelemetry.io/blog/2026/genai-observability/)

把重复的错误变成数据最小的用例，提出「财务退款新版的 `NA` 不计入」。同一份输入，旧版输出约 `(3, 3.33)`，候选输出 `(2, 5)`。在隔离回放中另测五条留出题，候选从 3/5 提到 5/5。再看权限，新增归档动作的候选仍被拦截。通过这两组检查，审阅者才可以激活带范围的候选。 [经验发布详细流程](evo-02-auditable-experience.md)

## 2. 灰度要看三项指标

灰度是先把少量请求交给候选版本。本次数据是模拟的，包含成功标记、总用时和成本。让旧版与候选处理同一类任务，再对照三项指标。成功率为成功数除以请求数。P95 是按耗时从短到长排序，取第 `ceil(0.95×n)` 个请求耗时，`n=4` 时等于最慢值。一次成功的成本等于所有请求成本除以成功数，失败仍消耗预算。少量固定样本只用于测试门槛与撤回逻辑。

| 组别 | 成功 | P95（毫秒） | 每次成功成本（分） |
| --- | ---: | ---: | ---: |
| 旧版对照 | 4/4 | 95 | 2 |
| 新版灰度 | 3/4 | 190 | 3 |

候选用了 `2+2+2+3=9` 分，有三次成功，所以平均每次成功 3 分。演示门槛为成功率至少 90%、P95 至多 150 毫秒、成功成本至多 3 分。新版虽然过了离线评测，但灰度模拟同时越过前两条阈值，审阅流程执行了回滚。正式发布应按任务类型、客群或批次配对，并记录样本范围和波动，不能用这四条当线上基准。 [Agent 灰度评测](../07-agent-eval/ae-08-regression-rollout.md)

## 3. 回滚后也需要把证据还给下一轮

实验留下 `v2 → v1` 的活跃版本变化，以及观察者提交、错误激活拒绝、审阅后发布和回滚的事件。上线后要核实新请求的路由、在途请求及已有产物。修正记录继续保留独立的版本号与来源。下一轮可以先查看延迟来自哪一段，并补进固定回归集，再考虑是否修改下一版。模型参数无需变化，程序也可借由同样的反馈回路提出输入校验、重试规则或覆盖新用例。

运行 `python3 experiments/agent-evolution/feedback_lab.py`，分别查看 `clusters`、`canary_simulation` 和 `audit`。本次回放只用合成事件，未接入线上流量。 [回放代码](../../experiments/agent-evolution/feedback_lab.py) · [完整结果](../../experiments/agent-evolution/feedback-results.json)

## 4. 从小脚本接到真实程序时，保留三个边界

| 边界 | 最小输入或输出 | 要单独核对什么 |
| --- | --- | --- |
| 业务到观察者 | 只读、脱敏的事件与聚合指标 | 去重是否保留所有真正失败，有无敏感字段混入 |
| 观察者到评测 | 候选版本、原始证据编号、固定回放数据 | 保持对照、留出题与预算口径，确认不触发线上写入 |
| 评测到发布 | 逐项结果、审批和撤回指针 | 失败时旧版恢复，审计留存当前版本和时间 |

普通程序不需要先具备自然语言能力，也能进入这个流程。比如每日退款任务已经会输出结构化事件，只需要让观察角色区分「字段含义用错」和「输入文件损坏」两类错误，然后提出复测用例。即使两个类别的失败数量都下降，也要看任务量是否变化。实际对照可以报告按千次请求的失败率，并保留原始分母，避免把低流量误读成质变。

灰度失败后也不要简单重复推送。分别追踪请求开始到发起统计的排队时间、工具执行时间和出报告后的传输时间。如果证据只能说明哪条阈值被触发，下一轮应先补能定位责任阶段的指标。 [结果与轨迹评测](../07-agent-eval/ae-02-outcomes-traces.md)
